# Windows 进程流量监控器设计

## 1. 目标

实现一个原生 C++ Windows 桌面程序，在 Windows Server 2016 及以上的 Desktop Experience 环境中，以管理员权限实时监控本机进程网络流量。

程序按“进程实例 + 传输层协议 + 推断应用协议”展示：

- 进程名称与 PID；
- TCP 或 UDP；
- 依据端口推断的常见应用协议；
- 上行累计字节与当前速度；
- 下行累计字节与当前速度。

首版只提供实时 GUI 展示，不提供控制台界面、曲线图、文件导出、数据库、远程管理或报文内容深度解析。

## 2. 支持范围

- 操作系统：Windows Server 2016、2019、2022、2025 及后续保持兼容的版本。
- 系统形态：安装 Desktop Experience；不支持 Server Core 和 Windows Server 容器。
- 架构：x64。
- 权限：应用清单声明 `requireAdministrator`。
- 工具链：C++20、CMake、MSVC、Windows SDK。
- 依赖：只使用 Windows API 和 C++ 标准库，不引入第三方运行库、GUI 框架、抓包驱动或测试框架。

## 3. 技术方案

### 3.1 采集方式

程序使用 Windows Event Tracing for Windows（ETW）的 SystemTraceProvider 网络事件。

启动一个仅属于本程序的实时系统记录器会话：

- 使用唯一会话名称和 GUID；
- 设置 `EVENT_TRACE_SYSTEM_LOGGER_MODE`；
- 设置 `EVENT_TRACE_REAL_TIME_MODE`；
- 通过 `EVENT_TRACE_FLAG_NETWORK_TCPIP` 启用 TCP/IP 网络事件；
- 不使用已废弃且容易冲突的固定 `NT Kernel Logger` 名称或 `SystemTraceControlGuid`。

采集范围包括 TCP/UDP、IPv4/IPv6 的发送和接收事件。事件自身的负载字段用于读取 PID，不能使用 `EVENT_RECORD.EventHeader.ProcessId` 代替，因为部分网络事件由其他线程记录。

ETW 只统计程序开始采集后的流量。程序不尝试恢复启动前的累计字节。

### 3.2 事件解码

不同事件类型和版本可能具有不同负载布局。解码器以提供者、事件类型/操作码、版本和指针宽度组成模式键：

1. 第一次遇到模式时，通过 TDH 读取事件元数据；
2. 查找 `PID`、`size`、`sport`、`dport` 等所需字段；
3. 构造并缓存该模式的解码布局；
4. 后续同模式事件依据缓存布局读取字段，避免逐字段反复调用低效的 `TdhGetProperty`。

无法完整解码的事件不进入流量统计，并增加“解析失败事件”计数。状态栏展示该计数，不把失败静默隐藏。

每个成功解码的事件转换为内部 `TrafficEvent`：

- PID；
- 方向：发送或接收；
- 传输层协议：TCP 或 UDP；
- 源端口和目标端口；
- IP 字节数；
- 采集时间点。

### 3.3 协议推断

协议推断只依据 TCP/UDP 和端口，不解析报文内容。界面必须明确将结果标记为“端口推断”。

首版包含以下映射：

| 端口/传输层 | 推断协议 |
|---|---|
| TCP 20/21 | FTP |
| TCP 22 | SSH |
| TCP 25/465/587 | SMTP |
| UDP 53、TCP 53 | DNS |
| UDP 67/68 | DHCP |
| TCP 80 | HTTP |
| TCP 110/995 | POP3 |
| UDP 123 | NTP |
| TCP 143/993 | IMAP |
| TCP 389/636、UDP 389 | LDAP |
| TCP 443 | HTTPS/TLS |
| UDP 443 | QUIC |
| TCP 445 | SMB |
| UDP 500/4500 | IPsec/IKE |
| TCP 1433 | SQL Server |
| TCP 3306 | MySQL |
| TCP 3389、UDP 3389 | RDP |
| TCP 5432 | PostgreSQL |
| TCP 6379 | Redis |
| TCP 27017 | MongoDB |
| 其他 | 其他 |

发送事件优先使用目标端口推断，接收事件优先使用源端口推断；若首选端口未命中而另一个端口命中，则使用另一个端口。两个端口都命中但结果不同时，使用方向对应的首选端口，保证规则确定且可测试。

### 3.4 进程识别与 PID 复用

首次观察到 PID 时，程序通过 Windows 进程 API 查询：

- 可执行文件名称；
- 进程创建时间。

聚合主键中的进程实例由 PID 与创建时间共同标识，避免 PID 被新进程复用后合并到旧统计中。

如果由于访问限制或进程快速退出而无法读取信息：

- 名称显示为 `受限进程 (PID)`；
- 使用 PID 和首次观察时间形成临时进程实例标识；
- 仍然统计流量。

进程结束后，其行保留并显示“已结束”，直到用户清零统计。

## 4. 数据聚合与速度计算

聚合键为：

`进程实例 + TCP/UDP + 推断应用协议`

每个聚合项保存 64 位无符号累计值：

- `sent_bytes`：上行累计字节；
- `received_bytes`：下行累计字节。

UI 每秒请求一次不可变快照。速度依据当前快照和前一次快照之间的字节差除以单调时钟的实际时间差计算：

- 首次出现的聚合项速度为 0；
- 时间差小于或等于 0 时速度为 0；
- 累计计数回退或清零时速度为 0；
- 速度单位为 B/s，并在显示层格式化为 B/s、KB/s、MB/s 或 GB/s。

累计量在显示层格式化为 B、KB、MB、GB 或 TB，换算基数为 1024，保留最多两位小数。

点击“清零统计”会原子清空累计项和速度基线，但不会停止 ETW 会话。

## 5. 并发与数据流

程序包含两个主要线程：

1. UI 主线程：创建 Win32 窗口、处理控件消息、按一秒定时器刷新表格。
2. ETW 消费线程：调用 `ProcessTrace`，解码事件并提交给聚合器。

聚合器通过短时互斥保护内部映射。采集线程只提交单个轻量事件；UI 线程一次复制完整快照，然后在锁外排序和更新控件。ETW 回调中不进行窗口操作，也不做可能阻塞的 UI 调用。

停止顺序为：

1. 标记停止请求；
2. 停止本程序创建的 ETW 会话，使 `ProcessTrace` 返回；
3. 关闭消费句柄；
4. 等待消费线程结束；
5. 释放窗口和应用资源。

程序只停止自己持有句柄和名称的会话，不枚举或停止其他会话。

## 6. 用户界面

程序使用 Unicode Win32 API 和公共控件 ListView，入口为 `wWinMain`，构建为 Windows 子系统程序，不显示控制台窗口。

主窗口包含：

- “开始采集/停止采集”按钮；
- “清零统计”按钮；
- 进程名筛选输入框；
- 流量 ListView；
- 底部状态栏。

表格列顺序为：

1. 进程名；
2. PID；
3. 状态；
4. 传输层协议；
5. 推断应用协议；
6. 上行累计；
7. 上行速度；
8. 下行累计；
9. 下行速度。

默认按当前上行速度与下行速度之和降序排列。点击列头可以按该列升序/降序切换。筛选不区分大小写，只影响显示，不影响后台统计。

界面每秒更新一次。刷新时按稳定聚合键复用现有 ListView 行，更新变化的单元格，并删除不再属于当前筛选结果的行；不在每次刷新时无条件重建整个控件。

状态栏显示：

- 当前采集状态；
- ETW 丢失事件数；
- 解析失败事件数；
- 最近一次不可恢复错误。

## 7. 错误处理

- 权限不足：由应用清单触发系统提升；提升被取消时程序不启动采集。
- ETW 系统记录器槽位耗尽：不停止其他会话，状态栏显示无法创建会话及系统错误码。
- 会话启动或消费失败：停止并清理已经创建的本程序资源，界面保持可操作，允许再次点击开始。
- 事件模式缺少必需字段：忽略该模式的事件并计入解析失败数。
- 进程信息查询失败：使用受限进程占位名称，继续统计。
- 字节计数加法溢出：饱和到 `UINT64_MAX`，不回绕。
- UI 关闭：无论当前处于采集还是停止状态，都执行幂等清理。

## 8. 文件与模块边界

- `CMakeLists.txt`：定义 GUI 可执行程序、测试程序、Windows 库链接和 CTest。
- `resources/app.manifest`：声明管理员权限和 Windows 兼容性。
- `src/traffic_types.h`：共享事件、聚合键和快照值类型。
- `src/protocol_classifier.h/.cpp`：纯函数端口协议推断。
- `src/traffic_aggregator.h/.cpp`：线程安全累计、清零和快照。
- `src/process_info.h/.cpp`：进程名、创建时间与存活状态查询。
- `src/etw_decoder.h/.cpp`：TDH 元数据缓存及事件负载解码。
- `src/etw_monitor.h/.cpp`：ETW 会话生命周期和消费线程。
- `src/formatting.h/.cpp`：字节数与速度显示格式化。
- `src/main_window.h/.cpp`：Win32 控件、定时刷新、排序和筛选。
- `src/main.cpp`：`wWinMain`、公共控件初始化和应用生命周期。
- `tests/unit_tests.cpp`：无第三方测试框架的确定性单元测试入口。

这些模块不创建通用插件、数据访问或依赖注入框架。只有不可直接测试的 ETW 边界与纯逻辑之间使用 `TrafficEvent` 数据结构隔离。

## 9. 测试与验收

### 9.1 自动化测试

CTest 运行一个原生测试可执行程序，至少覆盖：

- TCP/443 推断为 HTTPS/TLS；
- UDP/443 推断为 QUIC；
- TCP/UDP 53 推断为 DNS；
- 未知端口推断为其他；
- 方向首选端口和回退端口规则；
- 不同 PID、进程创建时间、传输协议和应用协议不会串流量；
- 发送与接收分别进入上行与下行累计值；
- 首次快照速度为 0；
- 已知时间差下速度计算正确；
- 清零后累计值和速度基线均重置；
- 64 位计数溢出采用饱和处理；
- B/KB/MB/GB/TB 与速度格式化；
- 默认速度排序和用户列排序；
- 已结束进程状态输出。

### 9.2 Windows 集成验证

在管理员身份运行程序后：

1. 启动一个 PID 已知的测试进程；
2. 由该进程产生 TCP HTTP/HTTPS 流量，确认对应 PID 的 TCP 行和上/下行累计值增长；
3. 由该进程产生 UDP DNS 流量，确认对应 PID 的 UDP/DNS 行增长；
4. 观察连续刷新，确认速度在传输时为正，停止传输后回落到 0；
5. 退出测试进程，确认行变为已结束且累计值保留；
6. 点击清零，确认历史行和速度基线清除；
7. 退出 GUI，使用系统 ETW 查询工具确认本程序会话不存在。

### 9.3 构建验收

- CMake 配置成功；
- x64 Debug 和 Release 均能编译；
- CTest 全部通过且无测试失败；
- Release 程序不打开控制台窗口；
- Windows Server 2016 Desktop Experience 上可以启动、提升权限并显示实时流量；
- 程序退出后没有遗留 ETW 会话或后台线程。

## 10. 已知限制

- 应用协议仅按端口推断，非标准端口、端口复用、隧道及加密内层协议可能显示不准确。
- 统计口径是 ETW 报告的 IP 事件字节，不等同于网卡线速字节，不包含所有链路层开销。
- 极高事件率或系统资源不足时 ETW 可能丢失事件；程序展示丢失计数，但无法补回数据。
- 最多可并存的系统记录器受 Windows 限制；槽位耗尽时程序拒绝采集而不干扰其他会话。
- 首版不支持 Server Core、Windows 容器、远程主机、ARM64 或 x86。
